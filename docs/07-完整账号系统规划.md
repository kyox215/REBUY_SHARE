# 完整账号系统规划

文档状态：G2-A0 账号安全合同输入；G1 Exit 前未打开，待独立安全审查与 Owner Gate
适用范围：Rebuy（临时名）多商家、批发与零售平台的账号、组织、权限、经营资格和隐私边界  
证据边界：本文是后续实现的规划合同，不代表认证、数据库、RLS、审核、MFA、Storage 或生产环境已经连接。  
数据原则：规划和示例只使用抽象字段与合成身份，不记录真实客户、商家、联系人、地址、邮箱、证件或其他 PII。

A0/A1 交叉合同：[A0 账号架构 ADR 与威胁模型](./09-A0-账号架构ADR与威胁模型.md) · [A1 Auth spike 执行合同](./10-A1-Auth-Spike执行合同.md)。

## 1. 目标、非目标与关键结论

### 1.1 目标

建立一套可供 Owner 评审、后续架构与测试直接引用的账号系统合同，覆盖：

- 游客、零售买家、批发公司、商家、商家员工和平台员工的完整路径。
- 认证 identity、组织/店铺 membership、角色权限 authorization、经营资格 verification 四层模型。
- 多组织、多店铺、店铺范围、邀请、商家入驻、批发认证和平台审核的状态与事务边界。
- 细粒度权限点、服务端授权、Postgres RLS、MFA、高风险重新认证、会话撤销、审计和安全通知。
- GDPR 数据最小化、私有证明文件、访问请求、删除与订单/财务留存的分离。
- 从短期 Auth spike 到小范围试运营的 A0–A6 阶段、风险、最小验证和 Owner Gate。

### 1.2 非目标

- 本 V1 不做微信登录、微信导入、微信同步、微信订单接入、微信 API 或微信专用数据架构；“微信电商管理”仍只是经营说法。
- Google 和 Apple 在 V1 只用于建立认证 identity；不读取 Gmail、Google Drive、联系人或 iCloud 数据，不保留 provider token，也不因此增加任何外部集成范围。
- 本文不锁定某个供应商的最终合同、区域、价格、版本或生产密钥，不创建数据库、路由、Storage bucket 或真实账号。
- 本文不把支付、分账、自动退款、税务、电子发票、物流、ERP 或原生移动端带入账号系统范围。
- 本文不以前端页面、客户端角色开关、URL 参数或 JWT 中可编辑字段作为授权根基。

### 1.3 关键结论

| 结论 | 规划要求 |
|---|---|
| 账号不等于商家 | 一个登录账号首先是 identity；只有通过 membership 进入某个组织/店铺，才具有组织内权限。 |
| 批发不是角色名 | 批发价格和起订量由经过审核的经营资格、组织状态、商品规则和服务端计算共同决定，用户不能手动切换。 |
| 用户不直接拥有店铺 | `users`/`profiles` 不直接挂 `store_id`；组织、店铺、成员和店铺 scope 是独立关系。 |
| 权限按点授予 | 角色只是可审查的权限集合；有效权限还受 membership 状态、组织/店铺 scope、经营资格、AAL 和动作风险约束。 |
| 默认拒绝 | Next.js 服务端授权层做请求级认证、授权、校验，Postgres RLS 做数据库最终边界；任意一层无法证明允许即拒绝。 |
| V1 三种账号入口 | 登录页提供使用 Apple 登录、使用 Google 登录和邮箱 OTP；Magic Link 作为兼容/后备，三个正式入口功能等价。 |
| OAuth 只建立 identity | Google/Apple 登录不能直接创建 membership、授予角色、批准商家或开放批发资格；业务授权仍由 Rebuy 数据库决定。 |
| 身份合并受控 | 同邮箱自动 linking 必须在 A1 实测；Apple relay 和重复业务用户必须进入明确的安全/人工恢复边界，不能猜测合并。 |
| 认证先做短期 spike | 当前推荐 Supabase Auth + EU 区域 Postgres/RLS/Storage + Next.js 服务端授权层，但必须先完成 A1 spike，再由 Owner 锁定。 |
| 高风险必须提高保证等级 | 平台 owner/admin/reviewer 强制 AAL2/TOTP；商家 owner/admin 在 Beta 前必须完成或直接强制；高风险动作必须重新认证。 |
| 审批必须原子化 | 商家批准时，组织、店铺、owner membership、scope、资格记录和审计事件要么全部成功，要么全部回滚。 |

| 决策 | 推荐选项 | 最晚门禁 |

| Apple OAuth 密钥责任 | `.p8` 保管人、约每 6 个月 secret 轮换、到期提醒、监控、演练与故障升级责任 | A1 / A6 |

## 2. 四层账号模型

四层必须使用不同表、状态和授权检查；任何一层的事实不能被另一层的客户端字段替代。

| 层 | 核心事实 | 典型实体 | 明确不代表 |
|---|---|---|---|
| 1. 认证 Identity | 证明“这个登录主体是谁”，包括邮箱验证、会话和 MFA 保证等级 | 供应商托管的 `auth.users`、业务侧 `profiles` | 不代表属于任何商家，也不代表拥有批发资格或平台权限 |
| 2. 组织/店铺 Membership | 证明“这个用户属于哪个组织、可进入哪些店铺以及成员关系是否有效” | `organizations`、`stores`、`memberships`、`membership_store_scopes` | 不自动授予所有组织能力，不绕过组织/店铺状态 |
| 3. 角色权限 Authorization | 证明“在当前上下文可以执行哪些资源/动作” | `role_definitions`、`permissions`、`role_permissions` | 不等于已通过商家或批发资质审核 |
| 4. 经营资格 Verification | 证明“该主体是否满足某项经营规则”，如商家入驻或批发采购 | `merchant_applications`、不可变的 `wholesale_applications`、`wholesale_qualifications`、`verification_documents` | 不改变登录身份，不自动赋予组织 owner 或平台管理员权限；批发申请历史不等于当前资格 |

有效授权可抽象为：

```text
允许 = 有效会话
     且 用户状态允许
     且 当前 organization/store 上下文来自有效 membership 和 scope
     且 角色包含所需 permission point
     且 组织、店铺、申请或资格状态允许
     且 AAL/重新认证满足动作风险
     且 服务端校验与 RLS 均通过
```

因此，`auth.users.email_confirmed_at`、客户端 `isWholesale`、用户可编辑的 `user_metadata`、URL 中的 `store_id` 或旧 JWT 中的角色字符串，都不能单独形成授权结论。

## 3. 账号路径

| 路径 | 进入方式 | 账号/组织结果 | 主要边界 |
|---|---|---|---|
| 访客 | 不登录即可浏览公开目录 | 临时会话购物车；不创建受保护的持久业务权限 | 只能看公开商品、商家、零售价和公开库存，不可提交订单或查看订单 |
| 零售买家 | 使用 Apple 登录、使用 Google 登录或邮箱 OTP；Magic Link 后备；验证后建立最小 profile | 有效用户，可拥有自己的购物车、订单、地址和售后；不要求组织 | 三种入口只建立 identity；自动显示零售价，可提交批发申请，但不能自行变成批发买家 |
| 批发公司 | 零售买家发起公司申请，或按政策由已知主体进入申请 | 审批通过后建立批发组织和 owner membership，用户获得有效批发资格 | 批发资格、组织状态和商品起订量共同决定价格；不能修改自己的审核结果 |
| 商家 | 已验证用户提交商家入驻申请，平台审核 | 批准事务原子化创建 merchant organization、store、owner membership 和 scope | 审批前不能经营、上架或读取商家后台；批准不授予平台角色 |
| 商家员工 | 由商家 owner/admin 邀请，指定角色与店铺 scope | 接受邀请后建立或激活限定 membership | 仅能执行 permission point 和 scope 覆盖的工作；不可自提权、转移 owner 或跨店铺读取 |
| 平台员工 | 仅由平台 owner/admin 邀请 | 平台组织或平台系统 scope 下的 membership | 不开放公共自助注册；reviewer、support、auditor 按职责分离，不能默认全平台写入 |

同一用户可以同时是零售买家、一个商家组织的 owner、另一个商家组织的员工和某个批发组织的采购成员。每次请求都必须明确且重新计算当前组织/店铺上下文。

## 4. 登录、会话与 MFA 策略

### 4.1 V1 登录策略

- **V1 正式入口：使用 Apple 登录、使用 Google 登录、邮箱 OTP。** 三个入口都能建立同等的 identity 会话；可以根据设备或平台合理排序，但不能隐藏、降级或让某个入口获得额外业务权限。
- **登录页遵守供应商按钮和品牌规范。** Apple 与 Google 使用各自官方允许的按钮、文案、图标、尺寸、对比度和同意页品牌配置；邮箱 OTP 使用 Rebuy 自有表单。三项保持清晰层级和足够留白，不堆成信息墙，也不把供应商按钮改造成容易误认的自制样式。
- **邮箱 OTP 是邮箱入口的主流程。** OTP 让用户在当前设备完成可见的验证码流程；Magic Link 作为兼容/后备路径，使用一次性、短时有效的 token，不作为第四个同级主按钮。
- **密码兼容后置。** 只有在真实用户研究、企业采购或迁移需求证明必要时才打开密码；届时必须补充密码策略、重置、防撞库和泄露密码检查。
- **明确不做手机短信登录、微信登录、微信扫码登录或微信账号绑定。** 业务分享链接不改变此边界。
- **Passkey 作为后续 Beta 评估。** 先验证设备兼容、恢复、跨设备和组织员工离职场景；评估通过前不把它写入 V1 必需路径。
- **生产必须使用自定义 SMTP。** 需要由 Owner 确认发件域、SPF/DKIM、退信、投诉、模板、域名对齐、速率和监控；供应商默认测试邮件不能作为生产方案。

邮箱输入、OTP 验证、Magic Link 消费、OAuth callback、会话刷新、退出和设备撤销都由受信任服务端协调。错误提示应避免透露账号或邮箱是否存在；OTP 发送、验证、重发和 OAuth 失败重试都要受速率限制。

### 4.2 Google OAuth 最小权限

- Google 登录只请求 `openid`、`email`、`profile` 三项最小 scope；供应商控制台可能把 email/profile 显示为完整 userinfo scope URI，但不得额外请求敏感或受限 scope。
- 登录只用于验证 Google identity 和取得最小 profile 提示，不代表读取 Gmail、Google Drive、联系人、日历或其他 Google 服务。
- Rebuy 不保存 `provider_token` 或 `provider_refresh_token`。如果未来需要调用 Google API，必须另开 Owner 决定，重新完成目的、scope、同意、token 加密、撤销、留存、隐私和安全评审。
- Google 控制台的 OAuth client、授权来源、redirect URI、品牌/同意页和发布状态按环境独立配置；用户取消授权、重复登录和同邮箱 linking 都在 A1 实测。

### 4.3 Apple OAuth、隐藏邮箱与密钥轮换

- 支持 Apple “隐藏我的邮箱”及 relay 地址；relay 邮箱是有效登录联系方式，不能强制用户提供或暴露 Apple 真实邮箱，也不能把 relay 邮箱当成异常账号。
- Apple Web OAuth 可能拿不到完整姓名，且姓名通常只在首次授权时可用。登录成功后通过渐进式 profile 补充显示名称；姓名为空不阻止登录，也不能用姓名作为身份合并依据。
- Apple 登录只建立 identity，不请求或读取 iCloud、联系人、照片或其他 Apple 服务数据。
- Apple Web OAuth 客户端 secret 约每 6 个月轮换。责任人、到期提醒、提前轮换窗口、监控、失败告警、回滚和紧急重签写入 A1/A6 运行手册并进行演练。
- Apple signing key `.p8` 只进入受控密钥系统，由最小权限角色访问；不得进入仓库、普通 `.env`、浏览器、日志、工单、截图或个人云盘。丢失或泄露时立即撤销并重建。

### 4.4 OAuth callback 安全

- 按具体 OAuth/SDK 流程启用并验证 PKCE、`state`、`nonce`；authorization code、PKCE verifier、state 和 nonce 都是短时、一次性并绑定发起会话。
- authorization code、PKCE verifier、state、nonce 和同类 OAuth 短时材料不得持久保存原值；消费后只保留必要的脱敏安全事件，例如 provider、结果、时间、环境、关联 session 摘要和不可逆事件标识。
- redirect 使用精确 allowlist；local、preview-staging、production 只允许各自登记的 origin/callback。回调后的 `next` 只能是服务端允许的相对路径或固定目标，禁止 open redirect、通配外域和客户端任意回跳。
- callback 先验证 provider、code、PKCE/state/nonce、环境、重放和会话，再建立 identity。取消授权、错误、账号不存在和账号冲突使用不泄露账号存在性的统一响应，并记录脱敏安全事件。
- local、preview-staging、production 的 Google/Apple client、secret、redirect、品牌/同意页配置完全独立，禁止用生产 client 或 secret 运行本地/预览环境。

### 4.5 Identity linking、unlink 与重复账号

- 一个 `auth.users` 用户可以关联 `email`、`google`、`apple` 多个 provider identities；登录方式是 identity 集合，不是多个业务 membership。
- Supabase 对同一已验证邮箱的自动 linking 必须在 A1 用 email→Google、email→Apple、Google→Apple、重复登录和取消授权矩阵实测后才能采用，不能只根据文档推断生产行为。
- Apple relay 邮箱可能与已有邮箱不同。不得按姓名、头像、未验证邮箱、客户端声明、组织关系、相似资料或客服主观判断自动合并。
- 手动 link/unlink 只能在用户已登录的安全中心发起，要求重新认证，校验目标 identity、当前会话和账号状态，并写安全事件、审计和通知。unlink 后必须至少保留一个已验证且可用的登录方式，禁止制造无法登录的孤儿账号。
- 如果不同登录方式已经生成两个业务用户，系统不自动搬运、合并或重写订单、购物车、地址、组织 membership、商家/批发资格、申请、审计或隐私请求。进入受审计的人工恢复/合并流程，先做所有权、法定留存、组织角色、重复订单、资格和冲突检查；具体合并/拒绝规则由 Owner 另定。
- Google/Apple OAuth 成功只建立或关联 identity；不得在 callback 中直接创建商家 membership、平台角色、商家批准结果或批发资格。

### 4.6 MFA 与保证等级

| 用户/动作 | 默认要求 | 规则 |
|---|---|---|
| 平台 owner/admin/reviewer | 强制 AAL2/TOTP | 未完成 TOTP enrollment 或当前会话不是 AAL2 时，阻止平台管理、审核和敏感读取。 |
| 平台 support/auditor | 按最小权限；访问受限安全/审计资料时 AAL2 | support 只收件、建工单、沟通补件并查看脱敏状态；auditor 只读审计/安全范围；二者都不能作审核决定。 |
| 商家 owner/admin | 强制，或最迟在 Beta 前完成 | 在试运营前不得让未完成 MFA 的 owner/admin 执行成员、权限、店铺停用和敏感导出。 |
| 商家其他员工 | 按职责和风险；高风险动作需 AAL2 | 不能用员工的低保证会话完成 owner 级动作。 |
| 普通零售买家/批发买家 | MFA 可选 | 账户安全设置可开启 TOTP；提交批发申请、变更关键资料或其他高风险动作可要求提升。 |
| 所有角色的高风险动作 | 重新认证 | 重新验证最近会话、必要的 AAL2 和当前 membership/状态；仅看 JWT 的 `aal` 不足以跳过实时校验。 |

建议高风险动作包括：批准或拒绝商家/批发申请、改变角色或店铺 scope、转移组织 owner、暂停组织/店铺、查看或导出证明文件、处理隐私删除/导出、撤销他人会话、重置 MFA、批量修改价格或库存、处理跨组织异常。每个动作应声明需要的 permission point、AAL、重新认证窗口和是否双人复核。

MFA 页面需要 enrollment、challenge、验证、设备/因子列表、撤销、**备用 TOTP 因子**和失去设备时的受审计人工恢复流程。备用 TOTP 因子必须登记在与主因子不同的设备或安全位置，不能把两个因子放在同一设备或同一可被同时拿走的存储位置。Entry preflight 候选建议（待 G2-A0 Owner 确认）：Rebuy V1 暂不采用静态恢复码；供应商能力仍待 A1 验证，Owner 未确认前不视为现行产品政策。人工恢复必须完成身份核验、职责分离、AAL/会话重置、限速、安全通知和追加式审计。恢复或解除 MFA 本身是高风险动作，不能由 support 单独批准。

### 4.7 会话、退出与撤销能力校准

- V1 先规划 Supabase 原生 `signOut` 的 `local`、`global`、`others` 语义，并在 A1 用独立测试环境验证每种语义、刷新 token、cookie 清理、并发请求和失败重试。
- 单设备列表、设备名称、单设备撤销和逐会话管理不是当前已承诺的 Supabase 能力。只有在 A1 验证 `auth.sessions` 的可见性、服务端权限、可用字段、RLS/管理 API 边界和实现方式后，才能把对应接口或 UI 标为可用。
- 被撤销的 access token 可能在其 `exp` 到期前仍被接受；因此高风险请求必须实时校验 `session_id`、当前用户状态、membership、组织/店铺状态和业务资格。普通请求按 Owner 批准的 JWT 时限运行，不把撤销假设写成即时 token 失效。
- 组织、membership、scope 或资格撤销仍必须立即阻断高风险业务动作；会话撤销结果、token 尚未过期的窗口和安全通知都要写入脱敏事件与审计。

## 5. 组织、多租户与上下文

### 5.1 关系规则

- `users` 不直接挂 `store_id`；认证用户由 `auth.users.id` 标识，业务资料在 `profiles`，组织关系在 `memberships`。
- `organizations` 是租户根，可区分 `merchant`、`wholesale` 和受限的 `platform` 类型；商家组织可拥有一个或多个 `stores`。
- `memberships` 至少包含 `user_id`、`organization_id`、`role_definition_id`、状态、邀请来源和时间边界；店铺限制放在 `membership_store_scopes`。
- `membership_store_scopes` 支持组织级、单店级或多店级范围。没有明确 scope 时，不得凭角色名推断“全店铺”。
- 同一用户可以加入多个组织，也可以在同一组织拥有一个主角色和经批准的附加职责，但最终权限必须由 permission point 合并规则计算。
- 平台角色可使用平台系统 scope，但仍需通过明确的 platform membership、职责、状态和审计策略；平台员工不因登录就获得商家数据。

### 5.2 上下文切换

1. 服务端根据会话读取用户可用的 active memberships 和 store scopes。
2. 客户端可请求切换上下文，但只提交候选 `organization_id`/`store_id`；服务端重新查 membership、scope、组织/店铺状态和目标 permission。
3. 服务端把当前上下文作为请求内不可变授权对象传给领域用例和数据库查询；不能复用上一次页面选择或只信任 cookie。
4. 组织、店铺、membership、scope 被暂停或撤销后，后续请求立即按数据库状态拒绝；缓存和旧 JWT 不能延长访问。

### 5.3 租户边界不变量

- 所有组织拥有的业务表带可信的 `organization_id`（文中简写 `org_id`）；若实现使用 `tenant_id`，必须由服务端/数据库关系派生，不能从请求体直接接受。
- 公开目录只能返回明确标记为公开的字段；商家内部成本、审核备注、供应批次、仓位和跨商家资料不属于公开租户。
- 跨商家订单批次没有单一商家租户；它通过买家、商家子订单和每个子订单的 `org_id/store_id` 形成分段访问。任何汇总读取都必须单独授权。
- RLS 查询路径要覆盖对象、组织、店铺、成员状态和作用域；“只在 UI 隐藏按钮”不构成隔离。

## 6. 角色与权限点

### 6.1 权限点目录

角色名只是可维护的集合名，不能作为代码中的唯一判断。每个权限点应有资源、动作、scope、风险级别、是否需要 AAL2、版本和审计策略。

| 权限点示例 | 作用 | 默认 scope/风险 |
|---|---|---|
| `profile.read_self`、`profile.update_self` | 读取或更新本人允许的资料 | user / 中 |
| `organization.read`、`organization.update` | 读取或维护组织资料 | org / 中 |
| `store.read`、`store.manage` | 读取或维护店铺资料与状态 | store / 高 |
| `member.read`、`member.invite`、`member.manage`、`member.revoke` | 查看、邀请、改角色/范围、撤销成员 | org/store / 高，AAL2 |
| `scope.assign`、`owner.transfer` | 分配店铺范围、转移组织 owner | org/store / 极高，AAL2、复核 |
| `catalog.read`、`catalog.write`、`listing.publish` | 商品、变体、上架和公开状态 | org/store / 中高 |
| `pricing.retail.write`、`pricing.wholesale.write` | 零售价、批发价、起订量和阶梯价 | org/store / 高 |
| `inventory.read`、`inventory.write`、`inventory.adjust` | 库存、单件设备、预留和调整 | org/store / 高 |
| `order.read`、`order.process`、`after_sales.manage` | 订单、子订单和售后工作流 | org/store / 中高 |
| `customer.minimal_read` | 读取订单/售后所需最小客户字段 | order/org / 高，按字段脱敏 |
| `support.intake`、`ticket.manage`、`supplement.communicate`、`redacted_status.read` | 收件、工单、补件沟通和脱敏状态 | assigned case / 中；不含完整证明或审核决定 |
| `merchant.apply`、`merchant.review` | 提交或审核商家入驻 | user / platform 高 |
| `wholesale.apply`、`wholesale.review` | 提交或审核批发资格 | user/org / 高 |
| `verification.document.read`、`verification.document.manage` | 查看或维护私有证明文件 | application/org / 极高，AAL2 |
| `platform.policy.manage`、`role.permission.manage` | 平台规则、角色和权限集合 | platform / 极高，AAL2、复核 |
| `security.events.read`、`sessions.revoke`、`mfa.policy.manage` | 安全事件、会话撤销和 MFA 策略 | platform/org / 极高 |
| `audit.read`、`audit.export` | 审计查询和受控导出 | assigned scope / 极高，AAL2 |
| `privacy.request.observe` | 只读观察隐私请求状态、期限、处理人和审计摘要 | assigned case / 高；只读，不得改变请求状态或输出资料 |
| `privacy.request.handle` | 实际执行导出、更正、删除、限制请求处理 | platform/org / 极高，AAL2、复核；只授予指定处理角色 |

### 6.2 角色矩阵

下表是 V1 的最小权限集合；实现时还要叠加对象归属、字段过滤、状态和 AAL。

| 角色 | 作用域 | 主要权限点 | 明确不能做 |
|---|---|---|---|
| 平台 `owner` | platform 全局，受高风险复核约束 | 平台策略、组织/店铺治理、成员和权限配置、商家/批发审核、安全、审计、指定的 `privacy.request.handle` 处理 | 不绕过审批、审计或 legal hold；不应单人无痕完成高风险变更 |
| 平台 `admin` | platform 分配范围 | `organization.*`、`store.manage`、被分配的审核、`member.manage`、`security.events.read`、受控审计 | 不默认拥有所有证明文件或任意导出；不能自批自己的申请 |
| 平台 `reviewer` | 被分配的申请/案例 | `merchant.review`、`wholesale.review`、必要的 `verification.document.read`、`audit.read` 案件范围 | 只能查看当前决定所需证明并作出审核决定；不改平台角色、权限、组织 owner，不读无关 PII，不批准自己处理的申请 |
| 平台 `support` | 被分配的账号/申请/支持案例 | `support.intake`、`ticket.manage`、`supplement.communicate`、`redacted_status.read`；订单/售后另按最小字段授权 | 仅收件、建工单、沟通补件和维护脱敏状态；不看完整证件，不写审核意见，不批准，不改组织权限或做全量导出 |
| 平台 `auditor` | 只读的审计/安全范围 | `audit.read`、`security.events.read`、必要的 `privacy.request.observe` | 只能只读观察隐私请求状态和审计摘要；不得执行隐私请求导出、更正、删除、限制或状态写入，不改业务、成员、角色或审批结果，不把 PII 导出到个人设备 |
| 商家 `owner` | 自己组织及明确店铺 | `organization.*`、`store.manage`、`member.*`、`scope.assign`、目录/价格/库存/订单/售后 | 不赋予平台权限，不读取其他组织，不清除平台审计；owner 转移需高风险复核 |
| 商家 `admin` | 自己组织/店铺 | 组织日常管理、`member.read/invite`（按策略）、目录、价格、库存、订单、售后 | 不转移 owner，不修改系统权限定义，不跨 scope，不读平台审核内部备注 |
| 商家 `catalog` | 指定店铺 | `catalog.*`、`listing.publish`、获准的零售/批发价格写入 | 不改成员、库存数量、客户资料或平台规则 |
| 商家 `inventory` | 指定店铺 | `inventory.read/write/adjust`、必要的订单库存协作 | 不改价格、成员、店铺 owner 或跨店库存 |
| 商家 `order` | 指定店铺 | `order.read/process`、最小客户字段、订单相关售后动作 | 不改目录、价格、成员或无关客户资料 |
| 商家 `support` | 指定店铺订单/售后运营 | `order.read`、`after_sales.manage`、`customer.minimal_read` | 只处理商家运营工单；不参与平台申请审核，不看平台完整证件、不写平台审核意见、不批准、不导出客户、不改库存/价格、不进入其他店铺 |
| 批发组织 `owner` | 自己批发组织 | 组织成员、采购和账务范围、批发资格状态查看、组织地址/资料 | 不批准自己的批发资格，不进入商家后台，不手动改批发价格 |
| 批发组织 `procurement` | 自己批发组织 | 目录读取、批发报价/资格读取、购物车、订单 | 不改账务、成员、认证文件或商家数据 |
| 批发组织 `billing` | 自己批发组织 | 组织账务资料和订单所需财务字段（支付范围另行审批） | 不改商品、库存、角色或审核结果 |
| 零售 `buyer` | 本人 user scope | `profile.*_self`、购物车、本人订单/地址、`wholesale.apply`、本人隐私请求 | 不看批发价格（除非资格有效）、其他买家、商家内部字段或成员权限 |

有效权限计算必须记录 `actor_user_id`、`membership_id`、`org_id/store_id`、permission point、资源 ID、结果、AAL、请求 ID 和策略版本。

## 7. 注册、邀请与审核流程

### 7.1 零售自助注册

1. 用户在 Apple、Google、邮箱 OTP 三个 V1 入口中选择一个；Magic Link 只作为邮箱兼容/后备，响应不透露账号是否存在。
2. Apple/Google 走受保护 OAuth callback；邮箱路径验证一次性 token、有效期、尝试次数、会话和邮箱确认结果。
3. 服务端建立或关联 identity，并按 A1 实测结论处理同验证邮箱 linking；OAuth 登录不能在此步骤创建 membership、角色、商家或批发资格。
4. 系统建立或更新最小 `profiles`，默认进入 retail buyer 路径；Apple 姓名缺失时在登录后渐进补充，姓名、地址和通知资料按业务任务逐步收集。
5. 购物车可以先保留为访客会话，登录后按明确的合并规则合并；合并不是授权升级，也不是重复业务用户合并。
6. 用户申请批发资格时，进入独立 `wholesale_applications`；申请记录与后续 `wholesale_qualifications` 分离，不能通过 OAuth provider、客户端字段或价格模式按钮改变身份。

### 7.2 商家申请与原子开店

1. 已验证用户创建 `merchant_application` 草稿，填写最小主体资料并上传到私有文件桶；申请草稿没有经营权限。
2. 提交后进入 `submitted`，support 只负责收件、建工单、沟通补件并维护脱敏状态；分配的 reviewer 才能查看当前决定所需证明、记录审核意见并作出决定。
3. 需要补件时进入 `needs_info`；申请人只能补充要求的资料，再由服务端重新提交并保留版本。
4. 通过审核时，服务端在单一事务中锁定申请并检查 `under_review` 状态，创建 merchant organization、首个 store、owner membership、店铺 scope、经营资格和审批事件。
5. 所有创建成功后才把申请改为 `approved`；任一组织、店铺、membership、scope、资格或审计写入失败，整个事务回滚，申请保持可重试状态并返回幂等结果。
6. 拒绝、撤回、暂停和重新申请不删除历史申请；批准不产生平台 owner/admin/reviewer 权限。

### 7.3 批发资格审批

1. 零售买家或符合政策的主体创建 `wholesale_applications` 草稿，明确申请人、拟采购组织和最小证明资料；申请审批历史与当前资格不是同一实体。
2. support 只收件、建工单、沟通补件并维护脱敏状态；reviewer 审核主体、业务用途、有效期和资料范围，查看必要证明并作出决定，不向其他角色暴露完整证件或平台内部审核备注。
3. `wholesale_applications` 进入 `approved`、`rejected` 或 `withdrawn` 后成为不可变审核历史；更正只能通过追加更正/复核事件或新申请表达，不能原地改写结论。
4. 批准事务原子创建或绑定 `wholesale_qualifications`，写入 `source_application_id`、`org_id`、`valid_from`、`valid_until`、`reason` 和递增 `version`，并绑定批发 organization、owner membership、组织 scope 和审计事件。
5. 只有 `wholesale_qualifications.status = active`、用户和组织都 active、membership 有效且商品规则满足时，才允许服务端计算批发条件。
6. 资格到期、暂停或撤销后，下一次价格和结算校验立即回到零售/不可购买规则；已有订单按订单快照和政策处理，不回写申请历史。

### 7.4 邀请规则

- 商家员工只能由商家 owner/admin 按 permission point 邀请；平台员工只能由平台 owner/admin 邀请。
- 邀请必须指定目标组织、可选店铺 scope、角色版本、目标邮箱的规范化摘要、过期时间和邀请人。
- token 只保存不可逆 hash；原 token 只在发送和消费时短暂存在；接受时绑定邮箱、组织、角色和 scope，并在事务中一次性消费。
- 接受邀请前，员工必须先证明对邀请目标邮箱的控制权。若当前 Apple/Google identity 的已验证邮箱与邀请目标邮箱不完全匹配（包括 relay 地址不匹配），必须拒绝接受；不得按 relay、姓名、头像或组织关系猜测为同一人。
- 允许的解决路径只有：先用邀请目标邮箱完成邮箱 OTP 验证，再在受保护的 link 流程中关联 OAuth identity；或由邀请人撤销旧邀请，并重发到已经由 intended employee 验证控制的新邮箱。link 是否可用仍须通过 A1 的 identity linking 实测。
- 重发会撤销旧 token；过期、撤销、已消费或 scope 已失效的邀请不可重放；接受邀请不会自动提高 MFA 或经营资格，除非门禁明确要求。
- 邀请人不能邀请自己成为更高权限角色；owner 转移、平台高权限邀请和敏感资料访问需要 AAL2 与复核。

## 8. 完整状态机与禁止动作

状态是服务端事实。客户端只呈现状态和允许的下一步，不能自行制造迁移。

### 8.1 `user` 状态

| 状态 | 允许转换 | 主要允许动作 | 禁止动作 |
|---|---|---|---|
| `pending_identity_verification` | `active`；超过政策期限可关闭 | 完成邮箱 OTP/Magic Link，或完成受信任的 Google/Apple OAuth callback | 访问受保护订单、组织、店铺或审核资料 |
| `active` | `locked`、`suspended`、`deletion_requested` | 依权限使用自己的账号和成员上下文 | 通过客户端自提权或绕过组织资格 |
| `locked` | 恢复后 `active`；风险确认前保持锁定 | 受限恢复、联系客服、查看安全通知 | 登录后继续业务写入、重置他人 MFA |
| `suspended` | 平台复核后 `active`；必要时 `deletion_requested` | 查看政策允许的通知和申诉入口 | 创建订单、接受邀请、管理成员或资料导出之外的业务动作 |
| `deletion_requested` | 处理后 `anonymized` 或 `deleted`；legal hold 可暂停处理 | 更正、导出、查看处理进度、撤回请求（政策允许时） | 新建组织/申请/订单；绕过留存策略物理删除交易事实 |
| `anonymized` | 终态 | 仅保留政策和法定需要的不可识别记录 | 登录、重新激活或读取原个人资料 |
| `deleted` | 终态 | 无业务访问 | 任何认证、授权和成员访问 |

### 8.2 `membership` 状态

| 状态 | 允许转换 | 主要允许动作 | 禁止动作 |
|---|---|---|---|
| `pending_acceptance` | `active`、`expired`、`revoked` | 仅通过对应邀请完成接受 | 读取组织数据、执行角色权限或自改 scope |
| `active` | `suspended`、`revoked` | 在当前 org/store scope 内执行 permission points | 跨组织/店铺、超出角色、在资格失效后使用批发能力 |
| `suspended` | 复核后 `active` 或 `revoked` | 查看撤销/申诉提示 | 任何组织写入、邀请、审批或数据导出 |
| `revoked` | 终态；需新邀请才能建立新 membership | 查看与本人相关的必要通知 | 依赖旧 session、旧 JWT 或缓存继续访问 |
| `expired` | 终态；需新邀请 | 无业务动作 | 接受旧邀请或恢复旧权限 |

### 8.3 `invitation` 状态

| 状态 | 允许转换 | 规则 |
|---|---|---|
| `created` | `sent`、`revoked` | 只保存 token hash、目标摘要和 scope；未发送的 token 也不可泄露 |
| `sent` | `accepted`、`expired`、`revoked` | 受有效期、尝试次数、邮箱绑定和邀请人权限约束 |
| `accepted` | 终态 | token 在同一事务中消费，membership 才能变为 active |
| `expired` | 终态 | 不可重放；重新邀请生成新 token 和新审计事件 |
| `revoked` | 终态 | 不能通过旧链接恢复；重发先撤销旧邀请 |

### 8.4 `merchant_application` 状态

| 状态 | 允许转换 | 主要规则与禁止动作 |
|---|---|---|
| `draft` | `submitted`、`withdrawn` | 申请人可补资料；不能上架、经营、读取商家后台 |
| `submitted` | `under_review`、`withdrawn` | 等待平台接收；申请人不能改变审核结论 |
| `under_review` | `needs_info`、`approved`、`rejected`、`withdrawn` | reviewer 只能处理分配范围；不能自审、自批或跳过证明文件权限 |
| `needs_info` | `submitted`、`withdrawn` | 只能补充所要求资料；旧版本保留，不覆盖审计历史 |
| `approved` | 记录完成；组织/店铺另有 `active/suspended/closed` 状态 | 只有原子开店事务成功后才能出现；不自动赋予平台角色 |
| `rejected` | 终态；新申请需新记录 | 不得把拒绝记录改写为批准或删除理由 |
| `withdrawn` | 终态；重新申请需新记录 | 只读保留必要记录和留存依据 |

商家组织或店铺被暂停时，不能把 `merchant_application` 改回草稿来恢复经营；必须走组织/店铺复核和审计流程。

### 8.5 `wholesale_applications` 审核历史状态

| 状态 | 允许转换 | 主要规则与禁止动作 |
|---|---|---|
| `draft` | `submitted`、`withdrawn` | 申请人可补资料；不能看批发价或改变起订量 |
| `submitted` | `under_review`、`withdrawn` | 进入审核队列；不能自行标记通过 |
| `under_review` | `needs_info`、`approved`、`rejected`、`withdrawn` | 审核需要主体、资料和政策条件；reviewer 不能自审 |
| `needs_info` | `submitted`、`withdrawn` | 补件后重新进入审核；不能沿用已撤销文件 |
| `approved` | 终态 | 只表示该次审核历史已批准；记录不可变，当前可用资格由 `wholesale_qualifications` 决定 |
| `rejected` | 终态 | 原申请记录只读保留，不原地改写结论；重新申请必须创建新记录 |
| `withdrawn` | 终态 | 保留最小审计与留存记录；重新申请必须创建新记录 |

进入 `approved`、`rejected` 或 `withdrawn` 后，申请记录的申请人、材料引用、审核意见、决定码和决定时间不可变。若需要纠正、复核或补充，只能追加版本化事件、关联人工处理记录或发起新申请。

### 8.6 `wholesale_qualifications` 当前资格状态

| 状态 | 允许转换 | 主要规则与禁止动作 |
|---|---|---|
| `active` | `suspended`、`expired`、`revoked` | 必须关联已批准的 `source_application_id`、`org_id` 和有效期；只有 active 资格参与批发价格计算 |
| `suspended` | `active`、`revoked` | 需要 reviewer/授权角色复核、reason、版本和审计；暂停期间不得显示批发价 |
| `expired` | 终态；新申请或新资格版本 | `valid_until` 到达即失效，不自动延长，不影响历史订单快照 |
| `revoked` | 终态；新申请或新资格版本 | 记录撤销 reason 和版本；不得通过旧 JWT、缓存或客户端样本恢复 |

每次资格状态变更都追加新版本，保留 `source_application_id`、`org_id`、`valid_from`、`valid_until`、`reason` 和操作者审计。资格不是申请的可编辑状态，也不是用户可修改的 metadata。

## 9. 核心实体与关键字段

字段表中的 `org_id` 是 `organization_id` 的简写；若实现采用 `tenant_id`，应把它作为可信租户边界并由数据库关系或服务端上下文派生。`NULL` 表示平台级或审批前尚未绑定组织，不表示可以放宽授权。

| 实体 | 关键字段 | `tenant_id/org_id` | 敏感性与边界 |
|---|---|---|---|
| `auth.users` | `id`、主邮箱、`email_confirmed_at`、`created_at`、`last_sign_in_at`、`email/google/apple` identities、供应商会话关联 | 无直接租户；provider-managed | 高；由认证供应商托管，一个用户可有多个 identity；业务表不复制密码、provider token 或完整身份元数据 |
| `profiles` | `user_id`、`display_name`、`locale`、`timezone`、通知偏好、资料状态 | 无直接租户；按 user 访问 | 高；最小 PII，Apple 姓名缺失时渐进补充；不能用 `user_metadata` 保存授权事实或做自动账号合并 |
| `organizations` | `id`、`type`、`display_name`、`legal_name`、`status`、`created_by`、`verified_at` | `org_id = id`，根租户 | 高；商家/批发/平台类型和经营状态分开维护 |
| `stores` | `id`、`org_id`、`display_name`、`slug`、`status`、`public_visibility` | 必须有 `org_id` | 中高；店铺状态不能覆盖组织成员授权 |
| `memberships` | `id`、`user_id`、`org_id`、`role_definition_id`、`status`、`invited_by`、开始/结束时间 | 必须有 `org_id` | 高；核心授权事实，唯一约束用户/组织/角色的有效关系 |
| `membership_store_scopes` | `membership_id`、`org_id`、`store_id`、`scope_type`、`status` | 必须同时校验 `org_id/store_id` | 高；防止把其他组织的店铺挂入成员 scope |
| `role_definitions` | `id`、`role_key`、`scope_type`、`version`、`is_system`、状态 | 平台全局或明确 `org_id` | 高；版本化，不能让组织管理员编辑平台系统角色 |
| `permissions` | `id`、`permission_key`、资源、动作、风险级别、AAL 要求 | 平台全局 | 中高；权限点目录是代码和审计的稳定合同 |
| `role_permissions` | `role_definition_id`、`permission_id`、`grant`、版本、变更人 | 跟随 role 的全局/org scope | 高；变更需高风险复核和审计，默认 deny |
| `invitations` | `id`、`org_id`、可选 `store_id`、目标邮箱摘要、`role_definition_id`、`token_hash`、过期/消费/撤销时间 | 必须有 `org_id`；平台邀请用 platform scope | 高；不存原 token，不公开目标邮箱和内部角色细节 |
| `merchant_applications` | `id`、`applicant_user_id`、拟用名称、资料引用、`status`、分配 reviewer、决定码、`org_id/store_id`（批准后） | 审批前可为 NULL；批准后绑定 `org_id` | 极高；申请资料和审核记录最小可见，批准必须原子开店 |
| `wholesale_applications` | `id`、`applicant_user_id`、拟采购组织、主体标识摘要/加密字段、资料引用、审核 `status`、决定码/时间、`org_id` | 审批前可为 NULL；批准后绑定批发 `org_id`；终态历史不可变 | 极高；只表达审核历史，不直接表达当前可用批发资格 |
| `wholesale_qualifications` | `id`、`source_application_id`、`org_id`、`status`、`valid_from`、`valid_until`、`reason`、`version`、创建/变更审计 | 必须绑定可信 `org_id`；由批准事务创建或版本化变更 | 极高；只有 `active` 且其他实时条件满足时参与价格/结算；不可由用户编辑 |
| `verification_documents` | `id`、`application_type`、`application_id`、`applicant_user_id`、可空 `org_id`、`storage_object_key`、文档类型、上传者、状态、保留到期日、文件摘要 | 审批前允许 `org_id = NULL`；归属必须由申请三元组 `application_type/application_id/applicant_user_id` 形成；批准事务成功后绑定 `org_id` | 极高；私有桶、短时签名 URL、禁止公开列举和永久直链；仅凭 `org_id IS NULL` 绝不放宽访问 |
| `consent_records` | `id`、`user_id`、可选 `org_id`、目的、法律依据、政策版本、语言、采集/撤回时间、证明引用 | user 或明确 `org_id` | 高；保留同意版本与目的，不用模糊的“同意全部” |
| `security_events` | `id`、actor、可选 `org_id`、事件类型、结果、AAL、session_id、`ip_hash`、粗粒度设备信息、时间 | 可选 `org_id`；平台事件可无租户 | 高；不写原始 PII、token、证件或完整请求体 |
| `audit_logs` | `id`、actor/service actor、`org_id`、`store_id`、目标类型/ID、动作、前后状态摘要、request_id、时间 | 目标属于 `org_id/store_id` | 高；追加式、受控读取，不允许普通成员清除或改写 |
| `privacy_requests` | `id`、`user_id`、可选 `org_id`、请求类型、状态、收到/期限/完成时间、legal hold、处理人 | user 或明确 `org_id` | 高；删除、导出、更正、限制请求需要最小访问和全过程审计 |

以下关系与 04 的核心模型保持一致：组织拥有店铺和成员；listing、价格和库存跟随商家/店铺；订单批次可跨商家但商家子订单各自带 `org_id/store_id`；买家只能看到自己的客户资料、地址、订单和售后所需字段。

审批前证明文件没有组织可绑定是正常状态，但不是无主状态：服务端和 RLS/Storage policy 必须同时匹配 `application_type`、`application_id` 与 `applicant_user_id`，并核对申请当前状态、申请人身份、角色和文件引用关系。批准事务完成后才写入可信 `org_id`；任何只以 `org_id IS NULL` 作为读取条件的策略均禁止。

## 10. 授权、安全与信任边界

### 10.1 分层请求链

每个 Next.js server action/route 按下列顺序执行：

1. 解析并校验 cookie/session，确认用户、会话状态和请求来源。
2. 对表单、路径参数、文件类型、分页、排序、组织/店铺候选值做 schema 校验；所有浏览器输入视为不可信。
3. 读取当前 user 状态、membership、store scope、组织/店铺状态、经营资格和动作风险。
4. 由统一 permission layer 判断 permission point、对象归属、字段范围、AAL 和重新认证窗口。
5. 通过领域用例和事务执行；返回最小、脱敏 DTO，不把内部成本、审核备注、完整证件、令牌或调试堆栈放入响应。
6. 数据库以 RLS 作为最终边界；Storage 也必须有私有 policy 和服务端签名访问。任何服务端授权遗漏都不能让其他租户读取或写入。

浏览器不得拥有或调用 service role；service role 不能进入客户端 bundle、公开环境变量、URL、日志、错误消息或浏览器 Network 响应。RLS 不是前端隐藏的替代品，前端也不能替代 RLS。

### 10.2 JWT、metadata 与实时事实

- 不使用用户可编辑的 `user_metadata` 授权，不把角色、组织、店铺、批发资格或审核状态放在用户可修改字段中。
- `app_metadata`、JWT 中的角色或组织声明可能陈旧；它们最多作为请求加速提示，不能成为高风险动作的唯一真源。
- 高风险操作、角色/ scope 变更、组织暂停、批发价格和结算前校验必须实时查询业务数据库中的 membership、状态、资格和当前会话/AAL，并由 RLS 再次验证。
- 修改角色、撤销成员、暂停组织或撤销会话后，应主动让相关会话失效或缩短刷新窗口；不能等待页面自然刷新来收回权限。

### 10.3 安全控制清单

| 控制 | V1 规则 |
|---|---|
| 默认拒绝 | 没有明确 permission point、对象归属、active 状态和 scope 时拒绝；空 scope 不等于全 scope。 |
| 反枚举 | 登录、邀请、申请、订单和隐私请求使用统一错误语义；ID 不连续或不可预测，访问不存在与无权访问尽量同形响应。 |
| OAuth callback | 验证 PKCE/state/nonce（按流程）、一次性 code、精确 redirect allowlist、环境绑定和重放；禁止 open redirect，错误不泄露账号存在性。 |
| Identity linking | 同验证邮箱自动 linking 先经 A1 实测；手动 link/unlink 需登录、重新认证、至少保留一个可用方式，并写审计和通知。 |
| 速率限制 | 按 IP、邮箱摘要、用户、设备/会话和动作组合限速；OTP 重发、验证、邀请、恢复和隐私导出使用独立预算，必要时加入 CAPTCHA。 |
| 邀请防重放 | token hash、短有效期、一次性消费、邮箱/组织/角色绑定、重发撤销旧 token、接受事务幂等。 |
| 幂等 | 用作用域化 `idempotency_key` 约束审批、邀请接受、成员变更、资格变更、隐私请求和其他高风险写入；重复请求返回同一结果或明确处理中状态。 |
| 会话撤销 | 先验证 Supabase 原生 `signOut` 的 `local`/`global`/`others`；单设备列表和撤销只有在 A1 证明 `auth.sessions` 可见性、服务端权限和实现方式后才可承诺；高风险请求实时查 `session_id` 与 membership。 |
| 安全通知 | 新登录、异常登录、MFA enrollment/撤销、角色/scope 变更、邀请接受、申请决定、会话撤销和隐私请求处理发送通知并写事件。 |
| 审计 | 记录操作者、组织/店铺 scope、目标、动作、结果、前后状态摘要、AAL、request ID 和时间；不记录原始 token、完整证件、密码或不必要 PII。 |
| 职责分离 | reviewer 不能审核自己的申请；support 只收件、建工单、补件沟通和维护脱敏状态，不看完整证件、不写审核意见、不批准；reviewer 才能查看必要证明并作出决定；审计和平台管理的读写范围分开；高风险导出、删除、owner 转移按 Owner 决定双人复核。 |
| 文件防护 | 证件和证明文件进私有桶；审批前按申请三元组和申请人归属授权，审批后再绑定 `org_id`；服务端授权后返回短时签名 URL；文件名、类型、大小、恶意内容和引用关系均校验。 |

### 10.4 2026-08-26 Entry preflight 不变量（待 G2-A0 Owner Gate）

本小节同步[G2-A0 Entry preflight 补充](./09-A0-账号架构ADR与威胁模型.md#31-2026-08-26-entry-preflight-安全补充待-g2-a0-owner-gate)，不是新的实现授权。Entry preflight 候选建议（待 G2-A0 Owner 确认）：Rebuy V1 暂不采用静态恢复码；供应商能力仍待 A1 验证，Owner 未确认前不视为现行产品政策。用户删除、暂停、membership/资格撤销和 MFA 恢复不得依赖旧 token 即时失效；A1 观察 session/token 时间窗口、会话状态和并发行为，A3/A4 验证业务拒绝与跨租户负向证据。

- Data API grants 与 RLS 是两层控制；暴露对象必须有显式 allowlist，publishable key 不是授权边界，服务端授权、RLS、Storage policy 和业务状态共同决定访问。
- 可更新对象必须同时满足 `SELECT` 能力以及旧行 `USING`、新行 `WITH CHECK`；view 要使用 `security_invoker` 或等价非暴露保护；`SECURITY DEFINER` 仅在必要时采用，固定 `search_path`、schema-qualified 引用、撤销 `PUBLIC EXECUTE` 并按角色 allowlist 授权。
- Storage `upsert` 必须覆盖 `INSERT`、`SELECT`、`UPDATE`；自有对象不得写入供应商 managed `auth`、`storage`、`realtime` schema。完整业务 RLS、view/function、Storage 和审批/租户负向测试留在 A3/A4。
- Entry preflight 候选建议（待 G2-A0 Owner 确认）：建议 V1 暂不采用 phone/SMS MFA；Owner 采纳后 A1 才可不测试该路径，若不采纳必须先修订 A1 合同并重新评审。供应商实际能力与会话/SSR 行为留在 A1 实测。

## 11. GDPR 与隐私边界

### 11.1 原则

- **数据最小化：** 只收集完成登录、订单、配送、售后、商家审核或批发审核所必需的字段；展示名称、地址和联系方式按场景逐步收集。
- **目的限制：** 登录联系方式不自动变成营销名单；证明文件只用于指定审核/合规目的；订单地址只给当前订单所需商家和授权客服。
- **访问最小化：** support 只看到收件、工单、补件沟通和脱敏状态；reviewer 才能看到当前决定所需证明；auditor 只读审计/安全范围，不能因“平台角色”读取全量 PII。
- **私有存储：** 证明文件、敏感附件和申请资料使用私有 bucket；只经服务端授权生成短时签名 URL，不产生公开直链或可枚举文件名。
- **日志脱敏：** 安全事件和审计记录使用 user/org/object ID、hash 或摘要，不写姓名、邮箱、电话、地址、证件原文、token 和完整请求体。
- **可追溯同意：** 记录目的、版本、语言、法律依据、采集和撤回时间；不使用无目的、无限范围的笼统 consent。

### 11.2 留存策略草案

以下是需要 Owner、意大利/EU 隐私顾问和税务顾问确认的策略框架，不是法律意见或最终期限。

| 数据类别 | 建议保留触发 | 处理方式 |
|---|---|---|
| 认证账号与 profile | 账号存续期间；删除请求完成后按必要性删除或匿名化 | 先处理未完成订单、申诉和 legal hold，再移除不必要资料；不复制 provider secret |
| OTP、Magic Link、邀请 token | OTP 为分钟级，邀请为短期窗口；消费/过期后不再保留原 token | 只保留 hash 和最小事件元数据；按安全审计需要决定元数据期限 |
| OAuth 短时材料 | authorization code、PKCE verifier、`state`、`nonce` 为一次性短时材料 | 不持久保存原值；消费、失败或过期后只保留必要脱敏安全事件和不可逆事件标识 |
| 商家/批发申请与证明文件 | 审核、补件、申诉和法定/合同留存所需期间 | 私有桶、短时访问；期限到达后删除文件并保留最小决定摘要 |
| 安全事件与审计日志 | 按安全、合规、争议和法定需要设置最短期限 | 伪匿名化、限制读取；不因账号删除直接抹掉必要审计事实 |
| 订单、交易和财务/税务记录 | 依意大利/EU 法定或合同留存要求 | 与账号删除分离；删除个人账号时对非必要个人字段匿名化，保留法定交易事实 |
| consent 与 privacy request | 为证明同意、撤回和请求处理所必要的期间 | 版本化、限制访问、写处理人和完成状态，不保存多余原文 |

删除不是把所有数据库行无条件物理清空：账号、组织成员和个人资料的删除/匿名化必须与订单、财务、税务、争议、审计和 legal hold 分开决策。

### 11.3 数据主体请求

客户端提供逐步入口，服务端建立 `privacy_requests` 并验证申请人身份和范围：

- **导出：** 生成可审计、最小且有时效的导出包；私有下载链接短时有效，不能把其他组织或商家资料混入。
- **更正：** 允许修改可更正的 profile/组织资料；对订单快照、审计事实和法定记录提供受限更正/附加说明，而不是无痕覆盖。
- **删除：** 先检查订单、财务、争议和 legal hold；关闭登录与成员关系，删除或匿名化可删除资料，保留必须留存的非必要个人字段之外的交易事实。
- **限制处理：** 进入限制状态后禁止非必要的新业务处理，但保留安全、法定和请求处理所需动作，并通知相关角色。
- **通知与申诉：** 每次请求有状态、处理人、期限、失败原因和可用的申诉/人工支持路径。

**上述字段、期限、法律依据、税务留存、跨境传输、处理者合同和删除例外必须由意大利/EU 法律与税务顾问最终确认。**

### 13.4 必须保持原子的操作

| 操作 | 事务内容 | 失败/重试规则 |
|---|---|---|
| 商家批准并开店 | 锁申请、校验状态和 reviewer 权限、建组织、首店、owner membership、store scope、资格、审计，最后改 `approved` | 任一步失败全部回滚；同一幂等键返回原结果，不生成第二组织或第二店铺 |
| 批发资格批准 | 锁 `wholesale_applications`，校验审核权限和状态，建/绑定批发组织、owner membership、`wholesale_qualifications`（含来源申请、org、有效期、reason、version）和审计 | 半成功不可见；申请终态与资格版本必须同一批准事务一致；重试必须读取原幂等结果 |
| 邀请接受 | 校验 token hash、过期、目标邮箱控制权、Apple/Google identity 精确邮箱匹配、角色/scope 和用户状态，消费邀请并激活 membership | 目标邮箱未验证或邮箱不匹配即拒绝；可先目标邮箱 OTP 再 link OAuth，或撤销重发；token 一次性消费，并发接受只能一个成功 |
| 角色或 scope 变更 | 重新认证、校验操作者权限、写角色/scope 版本、撤销受影响会话、审计和通知 | 不能只改缓存或 JWT；失败不应留下半个角色或半个 scope |
| 组织/店铺暂停 | 锁状态、阻断后续写入、处理/撤销成员会话、记录原因和通知 | 不删除历史订单；恢复需新复核和审计 |
| 删除请求受理 | 验证身份、建立 privacy request、检查订单/财务/legal hold、制定删除计划和通知 | 不立即清空所有行；重复请求幂等并合并到同一处理记录 |

## 16. 验收标准与负向测试

### 16.1 验收标准

- **四层可证明：** 测试能够分别证明 identity、membership、authorization、verification，不用一个 `role` 或前端开关代替四层。
- **三入口一致：** Apple、Google、邮箱 OTP 都能建立同等 identity；Magic Link 是邮箱后备，供应商按钮/品牌符合要求，入口排序不改变功能或业务权限。
- **Identity linking 可恢复：** 自动 linking 有 A1 实测证据；手动 link/unlink 需要重新认证且不产生孤儿账号；重复业务用户进入审计化人工流程，不自动搬运业务数据。
- **路径完整：** 游客、零售买家、批发公司、商家、商家员工、平台员工均有注册/邀请/审批/撤销和错误状态；平台员工无自助注册。
- **租户安全：** 任何读取、写入、搜索、排序、聚合、导出、Storage URL 和批次下钻都检查 org/store scope，RLS 与服务端授权一致。
- **撤销及时：** membership、组织、店铺或资格撤销后，旧页面、旧 session、旧 JWT、缓存和重试都不能继续执行受保护动作。
- **状态可靠：** 所有转换有前置状态、操作者、幂等键、审计事件和可恢复错误；半成功审批不可见。
- **高风险受控：** 平台 owner/admin/reviewer 与 Beta 前商家 owner/admin 满足 AAL2/TOTP；备用 TOTP 因子位于不同设备/安全位置；人工恢复有身份核验、职责分离、AAL/会话重置、通知、限流和审计；高风险动作有重新认证和必要复核。
- **隐私可审计：** PII 最小化、私有文件、短时签名 URL、日志无 PII；`privacy.request.handle` 只由指定处理角色在 AAL2/复核约束下执行，auditor 仅使用 `privacy.request.observe` 只读观察，导出/更正/删除/限制请求有状态和 legal hold 处理。
- **环境独立：** local、preview-staging、production 的项目、密钥、回调、Storage、RLS、SMTP 和数据互不混用。
- **证据边界清楚：** 文档、静态检查或本地预览不得被标作生产账号、真实审核、真实隐私处理或生产安全验收。

### 16.2 必须通过的负向测试

| 测试 | 预期结果 |
|---|---|
| 租户越权 | 用户 A 用用户 B 的 `org_id`、`store_id`、成员 ID、订单 ID、分页/聚合或 Storage 对象 key 请求时，读取和写入均拒绝，响应不泄露对象是否存在。 |
| 店铺 scope 越权 | 同一商家组织的员工访问未分配店铺时拒绝；组织级和店铺级 scope 不可互换。 |
| 撤销后权限 | membership、组织、店铺或资格撤销后，旧 session/JWT、缓存页面、并发请求和重试不能继续执行高风险动作。 |
| 过期/重放邀请 | 过期、已消费、已撤销、重发前旧 token、复制 token、错邮箱或已失效 scope 均拒绝，且不能创建第二 membership。 |
| JWT 陈旧 | JWT/app_metadata 仍含旧角色或资格时，实时数据库状态优先；角色降级/资格失效后的高风险动作拒绝。 |
| 审批半成功 | 故意让组织、店铺、owner membership、scope、资格或审计写入一步失败；事务回滚，不留下可运营半成品，重试幂等。 |
| MFA | AAL1 不能执行平台审核、权限、敏感文件、导出、删除和 owner 转移；备用 TOTP 因子必须在不同设备/安全位置；因子错误、撤销因子和人工恢复均限速、通知并审计，人工恢复必须身份核验、职责分离和 AAL/会话重置。 |
| 枚举/限流 | 不存在与存在邮箱、申请、邀请和订单 ID 的响应语义一致；OTP、邀请、恢复和导出超过阈值时拒绝或延迟。 |
| OAuth 业务提权 | Google/Apple 登录或 linking 只建立 identity；即使 provider 返回验证邮箱，也不能直接获得 membership、平台/商家角色、商家批准或批发价格。 |
| Google scope/令牌 | Google 同意页只出现 `openid`、`email`、`profile`；不能读取 Gmail/Drive/联系人，不保存 provider token。任何额外 scope 请求使验收失败。 |
| Apple relay/姓名 | 隐藏邮箱用户可正常登录且不被要求暴露真实邮箱；姓名为空或仅首次提供不阻断流程，也不能按姓名/头像自动合并。 |
| OAuth callback | 缺失/错误/重放的 PKCE、state、nonce、code，非 allowlist redirect、跨环境 client 和 open redirect 尝试均拒绝；错误不泄露账号存在性。 |
| Identity linking | Apple relay 不同、未验证邮箱相同、姓名/头像相似、客户端声称相同或组织关系相同均不得自动合并；unlink 最后登录方式必须拒绝。 |
| 重复业务用户 | 两个 identity 已形成两个业务用户时，不自动搬运订单、membership、商家/批发资格或审计；只建立待人工复核的冲突记录。 |
| PII 泄露 | 公共目录、错误响应、浏览器 DTO、日志、审计摘要、Storage 直链和缓存不包含未授权 PII、证件原文、token 或 service role。 |
| 隐私职责分离 | auditor 使用 `privacy.request.observe` 只能读取状态和审计摘要；任何导出、更正、删除、限制或状态写入必须由指定 `privacy.request.handle` 处理角色执行，未授权调用均拒绝并审计。 |
| 账号删除 | 删除请求不会绕过订单/财务法定留存；账号最终失去登录和 membership，非必要资料删除/匿名化，legal hold 记录阻止不当删除。 |
| 角色自提权 | 用户不能通过 `user_metadata`、表单角色、客户端 store 切换、篡改 JWT 或重复请求给自己增加 role/permission/scope。 |
| 会话与通知 | `signOut` 的 local/global/others 按 A1 实测语义生效；单设备列表/撤销只有在 `auth.sessions` 可见性和服务端权限验证后才承诺；被撤销 access token 可能在 `exp` 前仍有效，高风险请求实时查 session_id/membership；新登录、MFA、角色、邀请、审核和隐私处理产生安全通知与审计事件。 |

## 17. 当前推荐技术决策与替代评估

当前推荐：**Supabase Auth + EU 区域 Postgres/RLS/Storage + Next.js 服务端授权层**。理由是现有 04 已采用模块化单体、服务端信任边界和 RLS 方向，Supabase Auth 可覆盖 Apple/Google OAuth、邮箱 passwordless、identity linking、会话和 MFA 入口，数据库仍可承载 Rebuy 自己的组织、成员、permission point、verification 和审计真源。

这只是待 spike 验证的推荐，不是最终锁定。A1 应用同一组验收标准短期比较 Supabase、Clerk 和 Auth0 的：

- Apple、Google、邮箱 OTP 与 Magic Link 后备、custom SMTP、官方品牌/同意页、OAuth callback 和多语言通知。
- Identity linking/unlink、防孤儿、Apple relay/首次姓名、重复业务用户恢复和 Apple secret 轮换能力。
- Next.js 服务端会话、刷新、撤销、设备列表和异常恢复。
- TOTP/AAL2、强制 MFA、恢复、重新认证和高风险动作联动。
- 对组织/成员/permission point/RLS 的表达能力、调试性、区域和费用。
- 数据导出、删除、审计、供应商锁定和迁移路径。

无论选择 Supabase、Clerk 还是 Auth0，**组织、店铺、membership、scope、角色权限、商家/批发资格、审核记录和审计真源都必须在 Rebuy 业务数据库**；认证供应商只负责其授权范围内的 identity、会话和因子，不得成为可编辑的商家经营资格真源。
