# 项目总览与 V1 范围

文档状态：Owner 已批准方向的 V1 范围基线  
适用对象：产品、设计、架构、实现、测试和后续运营准备  
数据原则：本文件只使用虚构示例，不记录真实客户、商家、联系人、地址、邮箱、证件或其他 PII。

## 1. 权威定位与冲突处理

本文件把当前批准的产品方向整理成可执行的统一范围：

- 产品是面向批发和零售的多商家购物平台，不是普通单店商城。
- 商家可以申请入驻；平台审核通过后，商家建立并管理自己的店铺。
- 平台需要管理商家、客户、商品、分类、订单、售后、权限和操作日志。
- 客户端服务游客、零售客户和已认证批发客户。
- 当前批准只进入本地视觉原型，使用虚构数据、无 PII、无真实业务写入、无后端。

本项目未来可能会引用旧的供应商、批发或交易资料，但那些资料不自动成为当前范围。若历史资料与本文件或已经批准的 [客户端苹果风格设计规范](./01-客户端苹果风格设计规范.md)、[客户端 V1 页面线框图](./02-客户端V1页面线框图.md) 冲突，以本文件和已批准的 01/02 为准；冲突必须记录在新的 Owner 决定中，不通过修改旧文档来掩盖差异。

01/02 只约束买家客户端，因此其中“不设计商家后台”的表述与本文件“V1 规划包含商家管理能力”并不矛盾：前者是当前视觉原型的边界，后者是完整产品路线的业务范围。

## 2. 产品定位

这是一个 Italy-first、支持中文/意大利语/英语的响应式网站/PWA 方向多商家平台。平台连接两类供给与需求：

- 平台为商家提供入驻、店铺、商品、定价、库存、订单和售后管理能力。
- 平台为游客和客户提供跨商家商品发现、适用价格展示、购物车、结算、订单和售后入口。
- 认证批发客户不需要手动切换模式；系统根据可信身份和商品规则自动呈现批发条件。

它既承载普通数量库存商品，也承载必须单件购买的二手设备。二手设备的事实披露优先级高于装饰和促销表达。

## 3. 目标用户与核心价值

### 3.1 目标用户

| 用户 | 主要任务 | V1 需要解决的关键问题 |
|---|---|---|
| 游客 | 浏览、搜索、比较商品 | 不登录也能理解商品、商家、零售价和库存状态 |
| 零售客户 | 购买普通商品或二手设备 | 看见适用零售价，清楚商家边界，完成跨商家订单 |
| 已认证批发客户 | 按起订量和阶梯价采购 | 自动看到批发价、起订量和必要阶梯价，不被模式切换打断 |
| 商家 Owner | 管理店铺、商品、价格、库存和订单 | 在自己的组织/店铺范围内高效运营，不能访问其他商家数据 |
| 商家员工 | 执行被授权的商品、库存、订单或售后工作 | 权限按职责收敛，不能借员工身份改变组织权限 |
| 平台审核/客服 | 审核入驻和批发申请、处理支持与售后 | 能看到处理所需的最小资料，并留下可追溯记录 |
| 平台管理员 | 管理平台规则、组织、权限和风险控制 | 具备平台级运维能力，同时对高风险操作保留审计和复核 |

### 3.2 核心价值

1. **多商家清晰交易**：商品、购物车、结算、订单批次和商家子订单始终显示商家归属。
2. **价格自动适配身份**：零售用户看到零售价；已认证批发客户自动看到批发价、起订量和必要阶梯价。
3. **库存事实与商品类型匹配**：普通商品按数量库存，二手设备按唯一单件库存，并披露购买决策所需事实。
4. **商家可控且平台可治理**：商家有自己的店铺运营边界，平台保留入驻、权限、售后和审计能力。
5. **先建立可信的本地体验**：当前先验证买家客户端的结构、视觉和关键交互，不把静态预览误报为生产能力。

## 4. 业务边界

### 4.1 多商家模型

- 一个组织可以拥有一个或多个店铺；店铺是面向买家的经营边界。
- 同一购物车可以包含多个商家的商品，但展示、结算、金额、库存和订单状态必须按商家分组。
- 一次提交形成一个 checkout_batch，并按商家生成多个 merchant_order；客户端先展示订单批次，再允许下钻到商家子订单。
- 商家只能管理自己组织和被授权店铺的数据；平台不能把商家内部成本、仓位、供应批次或审核备注暴露给买家。

### 4.2 分类范围

平台分类至少覆盖以下一级类目：

1. 电子产品
2. 手机配件
3. 电脑与配件
4. 游戏/数码
5. 二手交易
6. 批发专区

分类体系由平台后台维护，允许后续增加、停用、排序或配置子分类。商品的展示分类和商家内部采购分类不是同一概念，不能用买家分类推断内部供应链字段。

### 4.3 商品、价格与库存

- 普通商品按数量管理，必须遵守可售数量、起订量、最大购买量和可选阶梯价规则。
- 二手设备按唯一单件管理，每件只能有一个可售数量；数量固定为 1，售出、锁定或失效后不得重复提交。
- 二手设备详情至少披露成色、缺陷/功能限制、电池健康或检测结果、保修范围/期限，以及必要的图片和配件事实。
- 零售用户看到零售价；已认证批发客户自动看到批发价、起订量和必要阶梯价。不得通过生产客户端的手动“零售/批发模式”切换改变价格。
- 所有价格、库存和批发资格在结算提交前重新校验；变化时必须指出受影响的商家和商品。

### 4.4 客户端体验边界

买家客户端采用简洁、直观、现代 iPhone App 风格，移动优先并响应式适配桌面。底部导航固定为：首页、分类、订单、购物车、我的；搜索放在顶部。半透明只用于导航、Sheet 等有限浮层，内容面保持清楚，不做全页玻璃化。

商家后台未来采用紧凑、专业、工作台式设计，不纳入当前买家客户端视觉原型，也不把买家端的卡片和底部导航直接复制到商家工作台。

### 4.5 “微信电商管理”的边界

“微信电商管理”只是经营说法，不是本产品的集成范围。平台不导入微信商品，不同步微信订单，不接入微信接口，也不建立微信专用模块。店铺和商品链接未来可以按普通网页链接分享，但分享不等于外部平台同步。

## 5. V1 包含清单

### 5.1 平台与商家治理

- 商家入驻申请、资料补充、平台审核、通过/拒绝/暂停和状态记录。
- 商家组织、店铺、成员和职责权限管理。
- 平台分类树及分类扩展能力。
- 商品、变体、店铺上架 listing、零售价/批发价、起订量和必要阶梯价。
- 普通商品数量库存、二手单件库存、库存变动记录和库存状态。
- 客户基本资料、批发认证申请和认证状态。
- 订单批次、商家子订单、订单事件和基本售后工作流。
- 细粒度服务端授权、RLS 设计、幂等约束和操作日志。

### 5.2 买家客户端

- 首页、分类目录、搜索/筛选、商品详情、购物车、结算、订单和我的。
- 游客浏览和临时购物车；登录客户查看自己的订单、地址和认证状态。
- 零售/已认证批发身份下的自动价格展示。
- 普通商品数量调整和二手设备单件购买事实展示。
- 多商家购物车分组、一次提交、订单批次和商家子订单查看。
- 中/意/英三语、深色模式、文字放大、减少动态效果和关键边界状态。
- 基于完全虚构数据的本地视觉原型，作为后续开发的交互合同。

### 5.3 技术方向

当前推荐方向是响应式网站/PWA，使用 Next.js App Router + TypeScript、模块化单体、Supabase PostgreSQL/Auth/Storage（欧盟区域）、RLS、Vercel、Tailwind CSS、shadcn/ui、GitHub/CI，并支持中/意/英三语。上述是规划方向，不代表版本已经锁定、环境已经创建、服务已经连接或网站已经部署。

## 6. V1 不包含清单

以下内容明确暂缓或排除，不得被 P1 本地视觉原型伪装成已实现功能：

- 在线支付与平台分账。
- 自动退款或自动赔付。
- 物流自动化、承运商接口和自动跟踪。
- 税务、电子发票和会计/财务自动化。
- ERP、仓储系统或采购系统连接。
- 原生 iOS/Android 应用；当前只规划响应式网站/PWA。
- 任何微信商品、微信订单、微信接口或微信专用后台能力。
- 复杂会员积分、复杂促销、优惠券规则引擎或营销自动化。
- 真实生产数据迁移、历史客户导入或未经批准的业务数据清洗。
- 在本地视觉原型中连接认证、数据库、Storage、支付、外部 API 或生产环境。

售后在 V1 中可存在申请、审核、沟通和状态记录，但不得把尚未批准的自动退款、在线支付或法定税务流程写成已具备能力。

## 7. 成功指标与证据

以下是待 Owner 确认的目标指标，不是已经发生的生产数据：

| 指标域 | 建议目标 | 需要的证据 |
|---|---|---|
| 发现效率 | 游客能从首页找到分类或搜索，并进入至少一个商品详情 | 本地任务检查、后续可用性测试 |
| 事实理解 | 普通商品能读懂价格/库存/商家；二手商品能在首屏找到成色、缺陷、电池和保修 | 视觉原型检查和任务脚本 |
| 角色正确性 | 批发身份自动显示适用批发条件，零售身份不暴露批发数据 | 身份矩阵测试、服务端授权测试 |
| 多商家理解 | 用户能理解一次提交对应一个批次和多个商家子订单 | 购物车/订单任务测试 |
| 数据隔离 | 组织、店铺、客户和内部商业数据跨租户不可见 | RLS、授权、负向测试和专项审查 |
| 可靠提交 | 重复点击或网络重试不产生重复订单 | 幂等测试、故障注入和订单事件核对 |
| 视觉质量 | 目标移动/桌面视口无横向溢出、遮挡、关键文字裁切和阻塞控制台错误 | 本地浏览器矩阵和构建检查 |
| 运营可追溯 | 入驻、价格、库存、订单、售后和权限变化有可查操作记录 | 审计日志设计和后续集成测试 |

## 8. 主要风险

| 风险 | 可能后果 | 当前控制 |
|---|---|---|
| 把单店商城思路带入多商家平台 | 商家边界、订单拆分和权限模型错误 | 以多组织/多店铺和批次/子订单为核心实体 |
| 批发价格泄露或身份失效仍可购买 | 商业损失和权限事故 | 服务端计算适用价格，结算前复核，RLS 和审计 |
| 二手设备事实不完整 | 用户无法作出知情购买决策，售后争议增加 | 成色、缺陷、电池、保修在详情首屏强制表达 |
| 普通库存与二手单件模型混用 | 超卖、重复销售或数量错误 | 分离 inventory 与 secondhand_units 语义，单件约束 |
| 多商家提交部分成功或重复提交 | 订单重复、状态不一致 | 批次/子订单、幂等键、事务边界、事件记录 |
| 本地原型被误认为生产完成 | 未验证的安全、隐私和商业流程上线 | 每份文档标明证据等级，P1 与生产验收分离 |
| PII 或商家内部数据进入前端/日志 | 隐私和商业信息泄露 | 最小 PII、私有资料、服务端 DTO、日志脱敏 |
| 范围继续加入支付、物流、ERP 等高风险能力 | 成本和验收不可控 | 暂缓清单和 Owner Gate；高风险专项审查 |

## 10. 执行结论

现在只打开 P1 本地视觉原型。后续实现必须引用 [本地视觉原型执行合同](./06-本地视觉原型执行合同.md)，并保持虚构数据、无后端、无外部连接。P1 达到首个有效预览门槛后，才由 Owner 决定是否进入认证、组织和权限纵切。
